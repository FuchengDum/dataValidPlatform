# 通用数据验证工具 - 经验总结与改进建议

## 1. 项目经验总结

### 1.1 成功因素

本项目在有限时间内形成了较为完整的产品形态，主要成功因素包括：

| 成功因素 | 具体体现 |
|---------|---------|
| **明确的产品定位** | 以赛题5验证业务价值、以CLI证明通用扩展能力，避免了能力过度包装为生产平台 |
| **双入口产品设计** | Web 工作台服务业务/测试用户、CLI 服务开发/工程化用户，二者协同但独立验收 |
| **可信规则智能化** | 以确定性规则为判定基础，AI 仅作辅助解释和候选推荐，保持结果可复现 |
| **结构化规则模板** | 优先通过配置化表达新增规则，避免了过度依赖业务编号硬编码分支 |
| **清晰的验收口径** | 使用状态标签（已实现/接入基础/后续规划/非本次承诺）避免承诺模糊 |

### 1.2 研发阶段回顾

项目演进经历了三个关键阶段，每个阶段都形成了明确的产出：

1. **第一阶段：业务核查闭环**
   - 以赛题5支付链路为核心场景（R020 金额核对、R029 重复支付）
   - 实现了从数据加载、规则执行、异常详情到报告导出的完整交互链路
   - 产出：Web 工作台、Spring Boot API、H2 seed 初始化、异常证据链

2. **第二阶段：旁路通用扩展**
   - 在同一后端工程中嵌入 CLI 通用验证内核
   - 实现了 YAML 规则包、文件/JDBC 数据源、机器可读输出
   - 产出：CLI 工具、generic-jdbc 非订单样例、case5-seed CLI 复现

3. **第三阶段：易用性增强**
   - 增加了 lint 配置校验、规则片段库、AI 辅助推荐候选
   - 提供了本地降级策略、来源标识和安全约束
   - 产出：CLI 易用性、安全边界、测试验证记录（164 测试通过）

### 1.3 关键决策与权衡

| 决策点 | 决策依据 | 权衡 |
|-------|---------|-----|
| **Web 与 CLI 规则资产分离** | Web 已有演示链路需保持稳定，CLI 独立验证通用性 | 不宣称异常集合完全一致，但复用模板执行能力 |
| **AI 不参与最终判定** | 确保确定性、可复现性和结果可信 | AI 仅作解释、SQL 草案和候选推荐，需人工确认 |
| **JDBC 只读约束** | 降低数据安全风险，避免对生产环境造成影响 | 真实业务库接入需补充账号治理、敏感数据控制等能力 |
| **Excel 报告非本次承诺** | 聚焦核心能力，避免分散精力 | 仅提供 Markdown/HTML 报告，Excel 作为后续规划 |

## 2. 技术实践经验

### 2.1 架构设计经验

**推荐架构模式：**
- 同一后端工程支撑 Web 与 CLI 双入口，复用领域类型和模板执行器
- 按入口分层：Web 交互层、CLI 命令层、通用内核层（规则执行、AI 辅助、数据访问）
- 明确边界：Web 演示链路、CLI 通用链路各自独立验收

**架构原则：**
1. **确定性优先**：异常判定由规则执行完成，不依赖 AI
2. **可追溯性**：异常关联规则、记录、实际/期望值和必要证据
3. **安全约束**：SQL 只读、候选不覆盖、来源可标识
4. **可复现性**：相同输入和规则得到相同结果

### 2.2 开发实践经验

**测试策略：**
- 后端单元测试覆盖：164 tests, 0 failures, 0 errors
- 前端构建验证：Vite 构建成功
- CLI 样例验证：generic-jdbc 和 case5-seed 的 lint 与 run
- 退出码语义验证：0（正常）、1（失败）、2（严重异常）、3（配置非法）

**开发实践要点：**
- 使用 Flyway 管理数据库迁移
- 通过状态标签明确交付边界
- 保留完整的验收记录和证据文件
- 对非交付能力明确标注为「后续规划」或「非本次承诺」

### 2.3 安全实践经验

**AI 安全约束：**
- AI 与规则执行解耦，不改变异常判定
- 辅助内容带来源标识（LOCAL_RULE_BASED 或模型来源）
- SQL 草案仅用于预览，不自动执行
- 模型不可用或非法时提供本地降级

**数据安全约束：**
- CLI JDBC 只读约束：拒绝多语句、注释、SELECT *、FOR UPDATE、危险函数
- 连接设置只读属性
- 密码通过环境变量提供，不写入源码或样例
- 候选规则只写新路径，不覆盖正式规则包

## 3. 产品与易用性经验

### 3.1 用户角色与场景

通过需求定义和验收观察，识别出两类核心用户及其关注点：

| 用户角色 | 核心场景 | 关注点 |
|---------|---------|-------|
| **业务/测试用户** | Web 工作台：加载数据 → 校验 → 定位异常 → 理解建议 → 导出报告 | 快速理解业务疑点、直观查看证据链、降低人工复核难度 |
| **开发/工程化用户** | CLI：lint → run → 消费结果 → 扩展规则 | 配置化接入、可复现执行、机器可读输出、易于流水线集成 |

### 3.2 易用性观察与改进空间

**已观察到的运行约束：**
1. 源码交付不包含构建的 Jar，新环境需先完成后端构建
2. 不同操作系统入口不同：Linux/macOS 使用 bin/data-validator，Windows 使用 bin/data-validator.cmd
3. generic-jdbc 样例的 H2 初始化脚本要求从 backend/ 目录执行
4. 部分环境需显式指定 JDK 路径（如 /opt/homebrew/opt/openjdk@11/bin）

**易用性改进方向：**
- 提供更完善的启动脚本，自动检测 JDK 路径
- 优化样例路径约束，支持从任意目录执行
- 增加友好的错误提示，帮助用户快速定位问题
- 提供开箱即用的二进制分发（可选）

## 4. 改进建议

| 改进项 | 优先级 | 实施思路 |
|-------|-------|---------|

| **Web 通用数据源** | 中 | 将 CLI 的 JDBC 只读接入能力延伸到 Web 交互路径 |
| **规则覆盖统计** | 中 | 在报告中增加规则覆盖范围、场景覆盖度等指标 |
| **易用性试用** | 高 | 完成两类目标用户的真实试用，记录反馈并迭代改进 |

## 5. 经验启示

### 5.1 给同类项目的建议

1. **明确交付边界，避免过度承诺**
   - 使用状态标签清晰区分已实现、接入基础、后续规划
   - 不要将演示样例包装为生产级能力
   - 尊重当前成果的局限性，如实告知用户

2. **优先验证业务价值，再考虑通用性**
   - 选择一个有代表性的业务场景（如本项目的支付链路）
   - 先形成完整的业务核查闭环，再考虑扩展到其他场景
   - 确保核心价值点（如 R020、R029）有充分的证据支撑

3. **重视可复现性与验收证据**
   - 保留固定的复现样例（如 case5-seed）
   - 记录完整的测试验证结果（如 164 测试通过）
   - 保存关键截图和报告文件作为验收证据

4. **安全约束要从设计时考虑**
   - AI 与业务逻辑解耦，避免模型输出影响判定
   - 数据访问设置只读约束，凭证通过环境变量提供
   - 辅助内容带来源标识，需要人工确认的环节明确说明

### 5.2 项目核心价值总结

本项目的核心价值不在于技术栈的新颖，而在于：

- **将业务规则转化为可执行资产**，减少人工跨表对账
- **将异常与证据关联展示**，降低问题理解和复核难度
- **提供双入口产品形态**，分别服务业务核查和工程化扩展
- **构建可信规则智能化闭环**，AI 辅助但不越权
