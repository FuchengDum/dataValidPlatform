# 通用数据验证工具 - 研发过程材料完整版

---

## 1. 项目概述与 AI 研发过程总述

### 1.1 项目概述

本项目面向"研发测试提效率"赛道中的业务数据准确性验证问题。赛题5提供订单、订单明细、商品、支付、库存流水 5 张业务表，以及 30 条规则、15 个校验场景和 7 条关联逻辑，适合验证数据在真实业务链路中的一致性，而不是仅检查字段格式。

项目最终形成一款通用数据验证工具：

- **Web 工作台**：服务于测试人员、业务用户，强调直观发现与解释异常
- **CLI**：服务于开发和工程化场景，强调规则扩展、数据源接入、可复现运行和流水线接入基础
- **确定性规则引擎**：负责异常判定，AI 负责推荐、解释和只读核查草案

### 1.2 核心问题与产品价值

传统人工核查需要跨订单、支付、库存等数据反复对账，存在规则分散、异常定位慢、证据不完整和结果不易复现的问题。本工具将业务规则变为可执行校验，将异常输出组织为"规则、记录、实际值、期望值、证据、原因、影响、建议"的核查链路。

**评审首个业务案例选择支付对账风险**：

1. `R020` 订单实付金额与支付金额不一致，展示跨表金额核对能力
2. `R029` 同一订单重复支付，展示可能造成资金风险的严重异常
3. 用户可在 Web 页面查看证据链、触发 AI 分析、生成只读核查 SQL 草案并导出报告

### 1.3 研发演进路线

| 阶段 | 解决的问题 | 已形成成果 |
|---|---|---|
| 选题与需求分析 | 找到适合形成完整核验闭环的赛题 | 选题分析、需求文档、验收场景 |
| Web 演示闭环 | 让业务异常可见、可解释、可导出 | Vue 工作台、Spring Boot API、H2 seed、异常详情与报告 |
| 模板化与 AI 辅助 | 从固定校验提升到规则推荐与分析辅助 | 结构化模板、推荐绑定、AI 分析、只读 SQL 草案与降级 |
| 通用 CLI 扩展 | 将能力推广到新的规则包和数据源 | `lint/run/validate/recommend/init`、文件/JDBC 样例 |
| 工程化基础 | 为自动化使用保留稳定接口 | 退出码、JSON/JUnit 输出、Case5 固定复现样例 |

### 1.4 双入口产品设计

Web 与 CLI 是同一工具的两种使用方式，而不是两个独立产品。

| 入口 | 目标用户 | 核心价值 | 主要证据 |
|---|---|---|---|
| Web 工作台 | 业务/测试 | 快速理解异常及其业务影响 | 汇总、筛选、详情、证据链、AI/SQL、报告 |
| 通用 CLI | 开发/工程化 | 扩展规则和数据源，批量或自动化执行 | YAML 规则包、JDBC 样例、lint、JSON/JUnit、退出码 |

当前 Web 与 CLI 的规则资产入口仍有差异：Web 的赛题演示链路使用既有模板绑定和内置兜底，CLI 的通用路径使用 YAML 规则包。因此材料只主张二者共同服务通用验证目标，不主张执行结果逐条完全一致。

### 1.5 AI 使用方式

项目的 AI 使用遵循"辅助而不越权"：

- Web 中，AI 可解释异常原因、影响和建议，并生成用于人工核查的只读 SQL 草案
- CLI 中，`recommend` 可在规则片段不足时生成候选规则建议，供人工审阅
- AI 不参与最终确定性异常判定，不自动覆盖正式规则包，不自动执行 SQL，不自动修改业务数据
- 模型不可用或输出不符合安全要求时，系统返回本地规则化结果或降级草案

### 3.1 总体架构

```text

            +----------------------+----------------------+
            |                                             |
       Web 交互核查入口                              CLI 工程化入口
    Vue 3 + Vite 单页工作台                 bin/data-validator / .cmd

            |                                     / recommend / --version
            v                                             v
    Spring Boot REST API                       Spring Boot 非 Web 模式
 Upload / Validation / Finding / Rule             GenericValidationCli
       AI / Report Controllers                            |
            |                                             |
            v                                             v
 ExcelImportService / ValidationService       GenericValidationRunner / Linter
 RuleBindingService / AiAssistService         AssetLoader / DataSourceProvider
 ReportService                                ReportWriter / AiAssistService
            |                                             |
            +----------------------+----------------------+
                                   |
                         TemplateRuleExecutor
          RowExpressionEvaluator / TemplateExpressionEvaluator
                                   |
            +----------------------+----------------------+
            |                                             |

```

### 3.2 Web 工作台系统设计

#### 3.2.1 端到端数据流

```text
用户上传赛题5 Excel
  -> UploadController / ExcelImportService 校验必需 sheet 并读取规则、场景资产
  -> BusinessTableDataProvider 从 H2 V3 seed 读取 5 张演示业务表
  -> 保存 dataset、table snapshot、rule definition、rule binding
  -> 用户查看规则绑定或应用人工确认后的推荐
  -> ValidationService 创建任务并执行确定性规则
  -> 保存 finding 与 evidence，查询汇总/详情
  -> 用户按需请求 AI/本地分析或只读 SQL 草案
  -> ReportService 生成报告文件并提供下载
```

#### 3.2.2 规则绑定与确定性执行

Web 导入链路从 Excel 规则资产生成 `RuleDefinition`，并由 `ExcelImportService` 为能够结构化表达的规则创建默认 `TEMPLATE` 绑定。执行时 `ValidationService` 遍历数据集规则：

1. 规则绑定为 `executorType=TEMPLATE` 时，交给 `TemplateRuleExecutor`
2. 未绑定模板或需兼容历史行为时，进入内置 `R001-R030` 规则分支
3. 校验任务、异常结果和证据均保存在系统库中

**当前评审演示重点**：
- `R020`：订单实付金额与成功支付汇总是否一致（`ORD002` 实付金额 `1580`，支付汇总 `3160`）
- `R029`：同一订单是否存在重复成功支付（`ORD002` 成功支付次数 `2`，期望 `<= 1`）

### 3.3 CLI 通用化系统设计

#### 3.3.1 定位与执行流

CLI 作为旁路通用验证内核，不替换现有 Web 演示链路。其目标是让开发或工程化用户通过配置资产和只读数据源执行确定性校验。

```text
init jdbc 生成接入起点 / 人工准备 validator.yml、source.yml、rules.yml
  -> lint 校验 schemaVersion、模板参数、表字段引用和安全配置
  -> run 或 validate 加载数据源和结构化规则包
  -> GenericValidationRunner 调用 TemplateRuleExecutor 产生 findings
  -> 输出摘要、报告文件和退出码
  -> 可选 recommend 生成需人工审阅的候选规则包
```

#### 3.3.2 配置资产与数据源

| 资产或数据源 | 作用 | 设计边界 |
|---|---|---|
| `validator.yml` | 组合数据源、规则包、报告与失败等级策略 | 当前支持 `schemaVersion: 1` |
| `source.yml` | 定义逻辑表、字段、主键和数据源配置 | 支持 inline、文件和 JDBC 只读读取 |
| `rules.yml` | 定义模板规则、严重等级和业务说明 | 新规则优先通过结构化模板表达 |
| JDBC 表或 SQL | 读取业务数据或派生规则字段 | 只允许显式字段的单条只读查询 |
| 候选规则包 | 保存 `recommend` 可审阅结果 | 只写新路径，不覆盖正式规则包 |

#### 3.3.3 输出契约与样例证明

| 样例 | 证明目标 | 当前固定结果 |
|---|---|---|
| `examples/generic-jdbc/` | 通用模板可用于非订单 JDBC 场景 | 2 条规则、2 张表、3 行、1 条严重异常，退出码 `2` |
| `examples/case5-seed/` | CLI 可使用 YAML 规则包复现赛题规模校验 | 30 条规则、5 张表、70 行、68 条异常（严重 60、警告 8），退出码 `2` |

### 3.4 规则执行与模板能力

当前模板能力能够覆盖以下类型的常见规则：

| 能力类型 | 当前模板示例 | 用途 |
|---|---|---|
| 字段约束 | `NOT_NULL`、`NON_NEGATIVE`、`NUMERIC_TYPE` | 必填、非负、数值类型 |
| 单行关系 | `FIELD_EXPRESSION`、`ROW_EXPRESSION` | 金额关系、状态条件 |
| 关联检查 | `EXISTS_IN_TABLE`、`RELATION_EXISTS`、`JOIN_ASSERT` | 跨表存在和字段断言 |
| 聚合核对 | `AGGREGATION_EQUALS`、`AGGREGATE_ASSERT` | 汇总金额一致性 |
| 重复检测 | `DUPLICATE_CHECK`、`DUPLICATE_ASSERT` | 重复支付等分组异常 |

### 3.5 AI 辅助边界

`AiAssistService` 当前提供三类辅助能力：

| 能力 | 触发方式 | 边界 |
|---|---|---|
| 异常分析 | Web 用户请求 `/api/ai/findings/{findingId}/analysis` | 生成原因、影响和建议，不改变 finding |
| SQL 草案 | Web 用户请求 `/api/ai/sql-drafts` | 始终返回 `executable=false` 的预览文本 |
| 规则推荐 | Web 推荐接口或 CLI `recommend` | 返回推荐/候选，必须人工应用或维护正式规则 |

### 3.6 安全控制

| 风险 | 当前控制 |
|---|---|
| AI 输出被误当作判定 | AI 与规则执行解耦，结果带来源与人工确认语义 |
| Web SQL 草案越权 | SQL 仅供预览，不自动执行；模型结果需满足只读和字段约束 |
| CLI JDBC 读取产生写操作 | 只允许 `SELECT`，拒绝多语句、注释、危险关键字、`SELECT *`、`FOR UPDATE` 和危险函数 |
| 数据库连接可写 | JDBC 连接设置只读属性 |
| 凭证进入配置或源码 | 拒绝明文 `password` 和 URL 敏感参数；MySQL 要求 `passwordEnv` |
| 推荐污染正式规则 | 候选只写新文件路径，不覆盖输入规则包 |

## 4. 关键节点、创新点与安全边界

### 4.1 创新主张

项目创新点不是让 AI 取代业务规则，而是建设"可信规则智能化"闭环：

1. **结构化规则模板**：将业务核验逻辑沉淀为可执行资产
2. **确定性执行器**：确保相同输入和规则得到可复现结果
3. **AI 辅助**：帮助解释异常和生成候选规则，减少理解与配置成本
4. **双入口设计**：Web 与 CLI 将同一能力分别带给业务核查和工程化扩展场景

### 4.2 创新证据矩阵

| 创新点 | 可展示证据 | 证明结论 |
|---|---|---|
| 支付风险核查闭环 | Web 中 `R020`、`R029` 详情与证据链 | 不只是字段校验，而是业务链路核查 |
| 模板化规则 | 规则工作台、规则片段库、YAML 规则包 | 新规则优先配置化表达 |
| 通用数据源 | `generic-jdbc` 样例 | 能从赛题场景迁移到新的只读数据源 |
| AI 异常解释 | Web AI 分析及来源标识 | AI 提升理解效率但不负责判定 |
| AI 规则候选 | CLI `recommend` 结果 | AI 辅助扩展，人工控制正式规则 |
| 自动化基础 | CLI JSON/JUnit 与退出码 | 具备进入流水线的基础接口 |

### 4.3 AI 安全边界

| 风险 | 当前约束 | 展示方式 |
|---|---|---|
| AI 判定不可信 | 最终异常由规则执行器判定 | 演示说明中明确 AI 仅辅助 |
| SQL 可能产生写操作 | SQL 草案仅用于预览，危险输出被拒绝或降级 | 保留只读草案与降级来源截图 |
| AI 候选污染正式规则 | 推荐只输出候选文件，不覆盖正式规则包 | 展示候选输出路径与人工确认说明 |
| 模型不可用 | 返回本地规则化分析或推荐 | 同时准备模型结果和本地降级证据 |

**只读 SQL 安全约束**：
- 仅允许 `SELECT`
- 拒绝多语句、注释
- 拒绝 `SELECT *`
- 拒绝 `FOR UPDATE`
- 拒绝危险写入关键字和危险函数

### 4.4 JDBC 与数据安全边界

- CLI JDBC 样例用于展示只读接入；真实业务库场景应使用只读账号
- SQL 数据源模式要求显式声明字段，不以任意 SQL 写入方式扩展能力
- 密码通过环境变量传入，不写入源码或提交样例
- Web 的真实生产业务库输入尚未作为当前交付能力

### 4.5 工程化边界

CLI 已实现可供流水线消费的基础结果形态和退出码语义，但以下能力仍是后续路线：

- 独立 `gate-summary` 文件
- 完整规则覆盖摘要和趋势展示
- 提交仓库内的正式 CI workflow 模板与阻断流程

因此材料使用"具备质量门禁接入基础"的表述，不使用"已建成质量门禁"的表述。

### 7.1 项目经验总结

#### 7.1.1 成功因素

### 7.2 技术实践经验

#### 7.2.1 架构设计经验

**推荐架构模式：**
- 同一后端工程支撑 Web 与 CLI 双入口，复用领域类型和模板执行器
- 按入口分层：Web 交互层、CLI 命令层、通用内核层（规则执行、AI 辅助、数据访问）
- 明确边界：Web 演示链路、CLI 通用链路各自独立验收

**架构原则：**
1. **确定性优先**：异常判定由规则执行完成，不依赖 AI
2. **可追溯性**：异常关联规则、记录、实际/期望值和必要证据
3. **安全约束**：SQL 只读、候选不覆盖、来源可标识
4. **可复现性**：相同输入和规则得到相同结果

#### 7.2.2 开发实践经验

**测试策略：**
- 后端单元测试覆盖：164 tests, 0 failures, 0 errors
- 前端构建验证：Vite 构建成功
- CLI 样例验证：generic-jdbc 和 case5-seed 的 lint 与 run
- 退出码语义验证：0（正常）、1（失败）、2（严重异常）、3（配置非法）

**开发实践要点：**
- 使用 Flyway 管理数据库迁移
- 通过状态标签明确交付边界
- 保留完整的验收记录和证据文件
- 对非交付能力明确标注为「后续规划」或「非本次承诺」

#### 7.2.3 安全实践经验

**AI 安全约束：**
- AI 与规则执行解耦，不改变异常判定
- 辅助内容带来源标识（LOCAL_RULE_BASED 或模型来源）
- SQL 草案仅用于预览，不自动执行
- 模型不可用或非法时提供本地降级

**数据安全约束：**
- CLI JDBC 只读约束：拒绝多语句、注释、SELECT *、FOR UPDATE、危险函数
- 连接设置只读属性
- 密码通过环境变量提供，不写入源码或样例
- 候选规则只写新路径，不覆盖正式规则包

4. 部分环境需显式指定 JDK 路径（如 /opt/homebrew/opt/openjdk@11/bin）

**易用性改进方向：**
- 提供更完善的启动脚本，自动检测 JDK 路径
- 优化样例路径约束，支持从任意目录执行
- 增加友好的错误提示，帮助用户快速定位问题
